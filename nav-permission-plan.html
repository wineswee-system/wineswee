全導航逐入口權限

讓上排每個 top tab、側欄每個入口，各自擁有一個可對「個別員工」開／關的權限開關 —— 自動生成、全涵蓋、以後新增頁面自動納管。

版本　v1 草案 日期　2026-08-06 範圍　導航可見性 / 路由存取 待你拍板

目標

「每一個入口都有開關」—— 不是模組群組那種粗開關，而是導航的每一格都能逐人控管：

  • 上排 top tab（商務營運 / 供應鏈 / 財務會計 / 人員組織 / 專案流程 / 數據分析 / 通訊協作 / 物流調度…）各一個開關；關掉整組連底下側欄都不見。
  • 側欄每個 leaf 入口（如 收銀台、菜單管理、客戶管理、庫存…）各一個開關；關掉只有那一格不見。
  • 關掉 = 該員工側欄看不到、直接打網址也進不去。
  • 權限頁自動照「top tab → 底下入口」層次列出全部開關，以後加新頁自動出現，不用手維護。

現況與缺口

現在的導航過濾集中在 src/components/Sidebar.jsx，靠兩張手維護的對照表：

  • GROUP_PERM — top tab → 一個粗權限碼（例：商務營運 → nav.group.crm）。但 CRM 和銷售共用同一碼，無法分開。
  • PATH_PERM — 約 50 條 leaf → 權限碼，只涵蓋部分頁。沒列到的入口（POS 全部、CRM/銷售/WMS 多數 leaf）等於對所有登入者開放。

結論：不是每個入口都有開關，而且粒度太粗、涵蓋不全、手維護容易漏。要達標就是把這套擴成全涵蓋 + 自動生成。

設計 — 兩層權限碼

唯一資料來源就是現有的 sidebarConfig.js（majorGroups 定 top tab、groupNav 定每 tab 底下的 section 與 leaf）。權限碼由它自動推導，不另外手列：

層級權限碼格式來源數量（約）
Top tab nav.top.<key> majorGroups 的 key（commerce、supply、finance…） 8
側欄入口 nav.entry.<path> groupNav 每個 leaf 的 path（/pos/menu → nav.entry.pos.menu） ≈ 150

碼的名稱＝入口中文名、分組＝所屬 top tab，全部由設定檔生成，所以權限頁與實際導航永遠一致，加新頁自動長出對應開關。

生效點（四處一致）

① 上排 top tab

majorGroups.filter(g => hasPermission(nav.top.<key>))；一個 tab 底下全部入口都被關才收起整個 tab。

② 側欄 leaf

每個 children 依 hasPermission(nav.entry.<path>) 顯示／隱藏。

③ 路由守門

進頁前依當前路徑檢查 nav.entry.*；沒權限 → 「權限不足」擋頁（擴充現有 PagePermGuard.jsx）。防止直接打網址繞過。

④ 權限頁

從 sidebarConfig 自動生成開關清單，照 top tab → 入口分組；取代手維護的對照表。

預設策略 — 需要你決定

關鍵決策

新權限上線那一刻，每個角色預設能看到哪些入口？這決定「會不會有人突然被鎖」或「會不會有人突然看到不該看的」。三個選項：

A · 沿用現況建議

用現行 GROUP_PERM / PATH_PERM 對照表推導：哪個角色現在看得到哪個入口，就把該入口預設開給那個角色。不放寬、不縮緊，上線零感知；admin 再逐人微調。生成時要對照現行對照表 + 角色預設，工比較細但最安全。

B · 全部預設開給所有角色有副作用

最簡單，上線沒人被鎖。但會放寬現有限制 —— 例如門市人員原本看不到薪資／財務，全開後會突然看得到，要 admin 事後逐一關掉。安全性倒退。

C · 只給 admin，其餘全關不可行

上線瞬間所有非管理員整個導航消失，要一格一格開回來，全公司停擺。僅列出作對照。

我的建議：選 A（沿用現況）。你先前提過「預設全開」＝選 B，我把副作用標出來讓你再定奪。

權限頁呈現

現有權限頁（員工個別權限）分兩塊功能：

  • 導航開關（新） — 自動列出全部 nav.top.* / nav.entry.*，照 top tab 摺疊分組，每組有「全開 / 全關」批次；約 160 個開關（量大但有分組、可搜尋）。
  • 功能權限（既有保留） — salary.compute、leave.approve 這類「能做什麼動作」的細碼不動，跟「能不能看到入口」是兩件事。

批次選多位員工一次套用的機制沿用現有，不重寫。

施工範圍與階段

migration（新）掃 sidebarConfig 產生每入口／每 tab 一個權限碼 + 依選定策略 seed 角色預設。以腳本讀設定檔生成靜態 SQL。
Sidebar.jsx拿掉手維護 GROUP_PERM / PATH_PERM，改用自動推導碼過濾 top tab 與 leaf。
PagePermGuard.jsx路由守門擴成依當前路徑檢查 nav.entry.*，未授權擋頁。
EmployeePermissions.jsx新增「導航開關」區塊，從 sidebarConfig 自動生成清單（分組 + 批次 + 搜尋）。
sidebarConfig.js補一個共用 helper（navPermCode(path) / topPermCode(key)）當單一真相來源，四處共用。

生成與種子

腳本掃設定檔 → 產生權限碼清單 + migration（seed 權限 + 依策略 A 帶入角色預設）。跑完 DB 有全套碼，但先不接生效點 → 零影響。

2

導航生效

Sidebar + 路由守門改吃新碼。此時「看得到 / 進得去」完全由新碼決定 —— 上線前重點驗收段。

3

權限頁

權限頁長出「導航開關」自動清單，admin 可逐人逐入口開關。

4

驗收

各角色實測（門市人員 / 行政 / 主管 / admin）側欄與網址存取；確認無人被誤鎖、無人越權。

風險與界線

最大風險 · 誤鎖

導航全面改吃新碼後，若某入口漏 seed，該員工就進不去。對策：super_admin 永遠放行（既有邏輯）＋ 守門「查無此碼時預設放行」保底＋階段 2 全角色驗收後才上。

  • super_admin org 為 null：既有已知情形，此案只碰導航可見性、不碰資料 RLS，不受影響。
  • 不在範圍：功能動作細碼（salary.compute 等）不動；資料列級 RLS 不動；LIFF 導航另案。
  • 量：約 160 個權限碼。權限頁用分組摺疊 + 搜尋，載入與操作可接受。
